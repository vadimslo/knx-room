3.1 Architecture specification: Substrate L1, subnet model, consensus

Tier 1 Filed, partial

In preparation. Architecture specification covering the L1 (a Bittensor subtensor fork on Substrate), the subnet model, Yuma consensus parameters and the deltas from the July 2025 whitepaper design.

Konnex runs a Rust and Substrate Layer 1 that is a fork of the Bittensor subtensor runtime: Aura block production at a 12 second target, GRANDPA deterministic finality, and subnets that run Yuma consensus as workload classes for physical AI. The layered design in the whitepaper (mesh, registries, miner markets, verification, economic loop) is the mainnet target; the public testnet exposes the subnet layer, an escrow pallet and on-chain evidence records, with stablecoin settlement and dual staking in build and mesh transport planned.

The chain as built

The testnet node identifies itself on the explorer as Subtensor Node 4.0.0-dev under the chain name Konnex Testnet. The runtime audited by SlowMist in April 2026 is described in the report as a Rust Substrate-based blockchain runtime fork of Bittensor with robotics-native coordination, subnet-aware task execution, escrow settlement, epoch execution and coinbase emission logic. The public repository konnex-world/konnex-chain-subtensor states the same origin.

Subnets as workload classes

A subnet is a workload class: a commercial pattern (aerial inspection, manipulation, 3D mapping) with its own input schema, scoring function and open miner competition. Subnets run Yuma consensus as inherited from subtensor: subnet validators stake on a subnet and score miner work, and emissions follow stake-weighted validator agreement. Joining subnet consensus is by neuron registration and subnet stake, and is independent of L1 block production. The four-role structure (subnet creators, miners, validators, stakers) is inherited from Bittensor; the differences are the workload (physical actions and artefacts rather than text), the Proof-of-Physical-Work (PoPW) record as the settlement trigger, and, on mainnet, stablecoin-native settlement with dual-staked validators.

Subnet creation follows a Substrate extrinsic flow: the creator holds the minimum KNX registration stake, defines a manifest (name, workload class, input and output schema, scoring function specification, miner and validator requirements, public code repository), submits the subnet-creation extrinsic which locks the stake and writes the metadata, receives a netuid on finalisation, enables emissions and publishes the miner and validator templates. The layered design in the whitepaper

The whitepaper (section 8) and the protocol architecture page describe four deterministic layers and one economic loop. Every packet's SHA-3 hash becomes its immutable JobID.

LayerComponentsFunction
Layer 0, Mesh and Gossiplibp2p and QUIC; channels task.*, bid.*, score.*, proof.*Signed JSON intents, bids with ETA and collateral, validator ScoreRoot each block, batched evidence references
Layer 1, Registry and Smart ContractsRobotIdentity, TaskRegistry, StakeVault, BondMatrix, PayoutRouterHardware-secured keys and trust score; stablecoin escrow, deadlines, penalties; dual staking with class-based slashing; third-party bonds; atomic payout
Layer 2, Intelligence and Motion MarketsMotion Miners, AI MinersTrajectories in a deterministic sandbox (Bullet3D with seeded RNG); perception and planning models as WASM weights or streaming endpoints; composite bids with on-chain fee splits
Layer 3, Verification and PoPWValidator council, deterministic replay (Wasmtime)Byte-for-byte replay, model audits against ground truth, PoPW completeness and binding check, single ScoreRoot per block with settlement in the same block
Economic loopStablecoins and KNXStablecoins for settlement and validator assurance; KNX for security stake, slashing, governance, fees; fee on stablecoin flows swapped to KNX for treasury

Finality targets stated for the design are under 10 seconds for simulation-only tasks and under 60 minutes with full PoPW evidence.

Deltas between the whitepaper design and the deployed chain

Three differences matter for a technical reader. First, the whitepaper's verification layer is a validator council with Wasmtime replay of trajectories; the deployed chain uses subtensor's Yuma consensus over validator weight vectors, with per-subnet verification running inside each validator's own node. Second, the whitepaper's TaskRegistry is a stablecoin escrow with PayoutRouter; the deployed runtime carries a konnex-escrow pallet in which a payer funds an escrow with a named set of resolvers, resolvers vote to release, and the payer can refund after the deadline (the pallet's extrinsics fund_escrow, vote_on_escrow and refund_after_deadline are the ones examined in the SlowMist audit). Third, the mesh transport, motion-miner sandbox and BondMatrix exist in the design only.
