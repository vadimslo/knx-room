3.3 Hardware root-of-trust design: how sensor data binds to device identity

Tier 1 Filed

The design binds sensor data to a device by signing telemetry and media in hardware, in a trusted execution environment or secure element, before the bytes reach a general-purpose host operating system, and by registering the device's hardware-secured key in the RobotIdentity registry with an on-chain trust score. Validators then check signature, freshness and binding to the signed task so that synthetic or replayed streams fail verification. On the testnet today every published evidence bundle is generated in simulation, so the hardware path has not yet been exercised on chain.

The whitepaper's data channels for evidence are video, GPS, IMU, torque and thermal; the SDK records camera, IMU, torque and thermal channels into a PoPW bundle. The whitepaper's Phase 2 extends the sensor set to IMU and LiDAR with hash anchors for data availability, and Phase 3 to a sensor-agnostic PoPW covering street cameras, thermal and pressure sensors.

Current state on the testnet

The latest evidence publications on all three live subnets (22 April 2026) carry verifier modes that name their simulation origin: ue_synthetic on drone-navigation (a frame captured in an Unreal Engine small-city environment by the validator itself), cosmos_warm_eval on robokitchen-vla (a kitchen simulator episode whose metadata names a Cosmos policy model), and hybrid on semantic-slam (a smoke-test round). In the public drone subnet code the executor role is played by miners answering a validator's synthetic frame; no device key signs the frame, and the validator's own wallet key signs the evidence hash remark. The SDK's robot attachment command takes a key file on the host (--keys./keys.json), which is a software key.

The commercial flows described for the three hardware partners state where a physical device stands today: the drone flow accepts a physical or simulated drone on the hardware link page; the kitchen flow uses a physical arm in deployment and a simulator on testnet; the mapping flow accepts a live stream from a mapping robot or a pre-recorded RGBD plus telemetry bundle. None of these flows has yet produced a hardware-signed evidence bundle visible on the explorer.

What the design leaves to implementation

The documents name the mechanism (TEE or secure element signing, RobotIdentity binding) but not the component. The choice of secure element or TEE, the key provisioning and rotation procedure, the attestation format that reaches the validator, and the on-chain form of the RobotIdentity record are implementation decisions scheduled with the mainnet registries (hardened task registry, identity and payout routers in Phase 1 of the roadmap).
